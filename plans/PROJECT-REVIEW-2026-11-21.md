# 项目复盘与升级建议（2026-11-21）

评估基线：提交 `4cb45dec89ed0a358512cd0784489de0cba1ce30`。日期与排期使用北京时间。本次为项目检查与规划建议；没有修改游戏事实、审核署名或生产代码，没有提交、推送或部署。

## 1. 结论

项目已经具备可持续扩充的静态双语攻略站基础。Astro、Markdown/JSON、Pagefind、Cloudflare Pages，以及来源/事实/译文修订、编辑预览和部署后验收的选择仍然合适。近期的战斗、资源、抽卡内容、快捷导航和手机操作条，总体沿着既有方向推进。

但近期扩展没有完整遵守原规划的内容质量与发布条件：新来源目前无法复核，礼包码时间存在逻辑矛盾，角色强度结论缺少对应证据，实体详情绕开了文章发布门槛，部分新事实被 schema 静默丢弃。应优先修复这些问题，再增加内容数量。

`22/22 可发布` 表示本地元数据和既有规则检查通过，不能解释为 22 篇正文的事实全部已经独立验证，也不能据此认定完整产品规划已经完成。

## 4. 优先整改问题

### R1 · P0：近期关键事实的原始证据目前不可复核

位置：`src/data/sources.json:337`、`:358`。

- 国服前瞻回顾 `https://azurpromilia.manjuu.com/home/news/detail/901234083139555331/`：HTTP 返回前端应用外壳，浏览器加载后进入 `/home/404`。
- 日本前瞻总结 `https://azurpromilia.jp/news/detail/1002`：直接 HTTP 请求返回 404，浏览器加载后回到官网首页。
- 两条来源均登记为 verified，支撑具体开服/预下载时刻、卡池规则、奖励等新结论。其 `evidenceFile` 指向的 11/14 研究记录没有对应的 11/20 核验内容。

本次结果只能认定当前证据链不足，不能单凭链接失效断定相关游戏信息为假，也无法证明该链接过去从未有效。

建议：从官方当前公告或官方视频恢复逐项证据，保存原文、核对日期、地区和视频时间点。无法恢复的结论应撤回确定性表述，按现有发布流程处理待核验状态与受影响双语稿。正文中的武器必定 UP、常驻 80 抽、代币永久有效、角色定位等，须分别核对，不能由一条概括性直播来源一并背书。

验收：每个影响下载、抽卡或奖励决策的结论都有能复核的对应原文；国服与日本分别成立。

### R2 · P0：礼包码时限与兑换方式互相矛盾

位置：`src/content/guides/zh-hans/redeem-codes.md:31`、`src/content/guides/zh-hans/resources.md:105`，以及对应日语稿。

文章写直播码在 11/23 23:59 截止，又要求在 11/26 开服后通关序章、进入设置兑换。在现有文字条件下，这条操作路径无法完成；若存在开服前网页兑换，应明确提供并核验真实入口。

复制组件 `src/components/RedeemCodeBox.astro:11` 只包含三组旧码，而正文新增的 `PROMILIA1120LIVE`、`STARVOYAGE2026`、`AZUR1126READY` 没有对应复制按钮。首页日语入口还承诺“一括コピー”，实际是前往文章。

建议：建立统一兑换码数据，至少包括 code、region、reward、availableAt、expiresAt、timeZone、redemptionMethod、sourceRefs、checkedAt、核验状态。正文表格、复制组件、首页状态共用该数据；未证实的码不展示“有效”“长期有效”或“全服通用”。到期停止推荐并保留失效记录。

验收：正文、按钮和首页展示同一批已核验码；适用区服准确；过期与兑换渠道相容；按钮复制值与所见值一致。

### R3 · P1：已发布强度和账号操作结论超出证据范围

位置：`src/content/guides/zh-hans/reroll.md:23`、`:45`、`:54`，以及对应日语稿。

正文给出西夫未瑟/忒拉拉 T0、艾妮丝群体治疗与净化、游客登录、清缓存重开、10—15 分钟到邮箱等结论，事实引用却仅包括日期和官网入口。这些来源不能充分支持角色强度和具体客户端操作。

建议：没有同版本实测或准确官方说明前，改为“是否值得刷初始的判断条件”，保留可验证的角色档案；移除确定梯队与未经验证的账号重置步骤。公测后按场景、版本、样本和操作条件形成推荐，再区分编辑建议和官方事实。

验收：读者不会因无证据的强度排名或账号操作建议作出错误资源决策。

### R4 · P1：新事实没有完整进入数据校验和影响追踪

位置：`src/lib/editorial-schema.mjs:52`、`src/lib/facts.ts`、`src/data/claims.json`、`src/data/distribution.json`。

- `cn-banner-rules-system.value` 新增的 `characterHardPity`、`weaponHardPity`、`beginnerPity`、`pityCarryOver` 等字段不在 schema 中；本次实测 `claimSchema.parse()` 后整个 value 变成 `{}`。奖励 value 的新字段也同样丢失。
- `jp-release-status` 仍是只有日期的 r2，具体日本开服小时没有独立结构化事实；正文和来源注释已写具体小时。
- `launch` / `getting-started` 正文写国服预下载日程，但未完整引用 `cn-preload-status`；刷初始稿也未引用支撑其奖励、卡池建议的新事实。相关事实变更后，现有检查不能完整拦截这些正文。
- `distributionRows()` 只向组件输出 `preloadUrl`，未输出已登记的预下载计划时间。因此即使某条预下载日程被标记已核验，设备速查仍可能显示“待核验”。“计划已确认、下载尚未开放”应分别展示。

建议：为日程、分发、卡池、奖励建立明确类型，未知字段报错；地区规则独立存储，事实依赖覆盖所有展示位置。不要把按语言翻译等同于按地区规则核验。

验收：结构化字段通过解析后完整保留；事实修订能定位并阻止所有过期展示；同一地区首页、文章和矩阵状态一致。

### R5 · P1：首页倒计时是固定文本

位置：`src/pages/[locale]/index.astro:33`。

“仅剩 6 天 / あと6日”没有根据时间计算，日期推进后仍不变；福利、时间也在页面和 i18n 中重复硬编码，绕开共享事实。艾妮丝在首页、实体与奖励事实间还出现不一致的“アニス / エニス”等日语写法。

建议：证据恢复后，用已核验地区时间驱动渐进增强倒计时，无 JavaScript 时显示固定绝对日期和时区。计时结束只表示已到计划时间；“已开服”必须来自独立确认。同步纠正日语术语。

验收：两地时区正确，跨日自动变化，结束无负数或自动开服声明；未知小时不生成倒计时。

### R6 · P1：实体详情绕过文章发布机制

位置：`src/data/entities.ts`、`src/pages/[locale]/characters/[id].astro:9`、`src/pages/[locale]/kibo/[id].astro:9`。

实体详情对全部实体无条件生成，无独立审核状态、事实修订和译文同步门槛，来源核对日期固定写为 11/14。只检查基础页面结构不足以保证新 CV、特性和奖励归属等字段已核验。角色 Person 结构化数据还把声优填为角色的 jobTitle，语义不准确。

建议：目录摘要与详情独立建模；能回答角色用途、获取或养成等具体问题的详情才开放索引。为实体字段关联来源、版本、审核及翻译状态，沿用现有影响追踪能力。资料薄的实体可以继续保留目录摘要，不必承诺完整资料库。

验收：修改实体证据后可定位双语页面；待审核详情不进入生产或索引；结构化数据描述与实际实体语义相符。

建议：保留清晰的历史记录，另设单一当前状态摘要；文章数、实体数、构建数、审核状态从报告生成。技术发布通过和事实审核完成分别记录。
