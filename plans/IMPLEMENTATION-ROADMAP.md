# 蓝色星原：旅谣攻略站实施方案

制定日期：2026-11-13；最新修订：2026-11-14。时间均为北京时间（UTC+8）。

本方案以用户提供的 2026-11-26 公测日期为排期前提，适用地区需回溯官方原始公告核验，不能自动扩展为全球同步发行。当前尚无应用代码，按从零建站规划。部署目标已确定为 **Cloudflare Pages**。用户于 11/14 确认已购买主域名 **promiliaguide.com**，并最终确定首版简中和日语，取消繁中，韩语后续补充；本方案按此调整范围与排期。域名已购不代表 DNS、Pages 绑定或部署已完成。

## 1. 产品定位与目标

定位：面向简体中文和日语读者的「开荒行动指南 + 可追溯资料库」。读者进入网站后，应能判断游戏现在是什么状态、自己下一步做什么、结论适用于哪个服务器和版本。主品牌 Promilia Guide，中文副标题可用「星原旅伴」。

首版核心承诺：

1. 把分散的官方公告、角色介绍、系统说明和测试经验整理成易查的页面。
2. 每篇攻略先给可执行步骤，再解释原因、前提和证据。
3. 对影响开荒决策的结论标注「官方已公布」「测试观察」「编辑建议」或「待核验」，并标明适用版本。
4. 公测后先校准下载、资源消耗、养成和抽卡等关键页面。

默认以 1 位站长配合 AI 编辑工具执行，每天可投入约 3—4 小时。双语首版减少独立主题和实体详情，复用事实库与模板，按语言分别校对；该投入是排期假设，不保证自动完成全部翻译。若校对速度不足，保留双语核心页面、减少次要内容。AI 负责抽取、归类、起草和翻译初稿；事实、名称与公开发布由编辑审核。

## 2. 首版范围

目标为 18—20 个基础内容主题，按语言分批覆盖，约 26—30 个可收录语言 URL；不含根语言选择页和关于、版权等辅助页面。简中 18—20 页、日语 8—10 页。未满足来源或校对条件的页面留在草稿，数量不能凌驾于质量。

| 简中基础页面组 | 主题数量 | 解决的问题 |
|---|---:|---|
| 首页 | 1 | 当前阶段与常用入口 |
| 发行、开服准备与开荒指南 | 9 | 公测时间、全球/国服发行状态、下载、平台、配置、开服准备、首日路线、资源规划、抽卡机制 |
| 核心系统指南 | 4 | 战斗与元素、奇波、家园、探索；养成先在角色/资源页解释 |
| 角色专题入口与详情 | 2—4 | 1 个目录 + 1—3 个有足够资料的角色页 |
| 奇波专题入口 | 1 | 已知奇波、用途和相关来源；详情后续补 |
| 公告索引与修订记录 | 1 | 首版合并管理，后续按需要拆分 |
| 基础主题合计 | 18—20 | 日语优先覆盖其中的核心主题 |

未公布的首日路线可以作为编辑草稿准备；若只有测试资料，公开页标题必须明确为「测试版开荒参考」，公测核验后再改为公测指南。充值建议、自选推荐、限时奖励等会影响资源决策的内容，没有足够证据时只列核对事项。

Trends 依据与内容调整：全球近 3 个月主题较此前 3 个月显示 +30%；明确的关联需求包括 release date、pre register 和 PC。首批优先发行日期、地区、下载与平台页面。地区相对指数不等于用户数量或流量份额；双语优先级同时依据用户 11/14 的语言策略确定。图鉴、强度榜与兑换码仍有产品价值，但未在本次全球 Top 50 中得到明确关键词验证。英文试点退出首版，韩语后续评估。详见 `TRENDS-RESEARCH.md` 与 `LOCALIZATION-PLAN.md`。

首版功能：双语目录、保持文章对应关系的语言切换、当前语言站内搜索、移动端导航、来源与服务器/版本标记、修订记录、轻量纠错入口。攻略步骤清单可用浏览器本地存储保存勾选状态。

用户已明确确认：**CMS、站内账号、评论在前期不纳入开发范围**，不为这三项预建后台、认证或数据服务。内容继续通过本地文件与 Git 维护。

其他首版暂缓项：独立交互地图、开放注册编辑、复杂配队或伤害计算器、全量装备数据库、韩语与英文内容。地图优先提供经核验的外部入口。

## 3. 信息采集与编辑流程

### 来源清单

优先收录游戏官网、官方 B 站和其他官方账号公开发布的公告、视频、图片与规则。视频记录标题、作者、发布日期、链接和关键时间点。将玩家测试实录与 BWIKI 等资料作为补充与交叉检查入口；引用第三方观点应注明作者，素材使用遵循授权条件。

建立两层记录：

- 来源记录：来源 ID、标题、作者/发布者、原始链接、发布日期、核对日期、对应版本、可访问状态、相关时间点。
- 结论记录：具体结论、所属主题、依据的来源 ID、结论性质、适用版本、核验状态、待解决的冲突、影响页面。

例如「某机制在测试中出现」应关联测试实录；「公测沿用该机制」需要公测公告或正式客户端证据，不能由前者自动推出。

### 每日工作流

1. 收集：检查固定官方来源，记录新增内容和日期。
2. 抽取：将一份公告拆成可核对的事实条目，保存链接和视频时间点。
3. 去重：相同事实归入已有条目；保留各来源，不重复生成文章。
4. 核验：冲突按版本、发布日期和来源性质拆开；无法解决则说明未知，不强行合并成结论。
5. 编辑：把事实转换成步骤、表格、条件和常见问题，给出原创解释。
6. 发布：核查标题、版本、来源和图片使用条件，运行构建与链接检查后人工发布。
7. 回访：来源变化或公测结果出现时，定位受影响页面并修订。

双语共用稳定内容 ID 与来源记录；日语需术语表和独立表述审核。记录 sourceRevision 与 translatedFromRevision，事实修改后把关联译文标为待更新。重大日期、下载和资源规则修订优先同步双语。名称未确认时保留原文并标注，不杜撰官方译名。

每天安排约 30—45 分钟核对信息，其余时间用于正文、数据整理和页面体验。第一天建立来源目录，以后增量维护。

### 文章与图鉴模板

攻略页：一句话结论 → 适用版本与前提 → 操作步骤 → 资源成本/例外 → 常见问题 → 来源 → 修订记录。

角色页：已公布定位 → 技能说明 → 已确认机制 → 养成入口 → 有依据的使用建议 → 未确认项 → 来源。没有证据的倍率、材料数量、强度排名不填猜测值。

奇波页：用途 → 获取条件 → 探索/战斗/家园能力 → 测试版本差异 → 来源。获取位置没有可靠证据时明确缺项，不生成虚假点位。

内容达到「能解决一个具体问题、有来源、能说明适用版本」后才发布。资料不足的角色可先在目录里显示简短已知介绍，不生成可收录的空详情页。

## 4. 技术建议

采用 Astro + TypeScript + 内容集合（Markdown/MDX）+ Pagefind，完全静态输出到 **Cloudflare Pages**。这个阶段文章和图鉴占主导，静态方案便于快速上线、搜索抓取与回滚。首版不需要 SSR adapter 或 Pages Functions。

- 攻略用 Markdown/MDX；角色、奇波、来源记录用 YAML 或 JSON，构建时校验字段。
- 所有关键正文和内链输出为 HTML；少量交互独立加载。
- URL 采用 `/zh-hans/`、`/ja/`；根路径提供语言选择。内容语言与游戏服务器分别建模，不按 IP 强制跳转。
- Pagefind 用于当前语言站内搜索，实施时验证中文/日语检索与别名；没有搜索结果时提供目录入口和反馈方式。
- 各语言页自引用 canonical，仅在已发布的对应文章之间生成双向 hreflang。缺译文不生成空页；韩语入口在内容准备好后启用。
- 用 Git 管理内容与变更；Cloudflare Pages 连接仓库，分支/PR 生成预览，合入生产分支后构建发布。Pages 统一使用 `npm run build:pages`，按显式环境模式及实际分支校验：生产调用 `build:release` 先检查首发核心稿件，分支调用 `build:preview` 生成 noindex 草稿预览。两个环境设置 `PAGES_BUILD_MODE` 和实际 `PAGES_PRODUCTION_BRANCH`，详见部署文档。日常开发/CI 继续使用 `npm run build` 验证生产隔离，本地编辑预览使用 `npm run build:preview`，可用 `npm run review:bundle` 交接同批正文与证据。
- 先用站内结构和少量真实内容确定组件，再批量录入，减少模板返工。
- 前期由本地文件编辑，使用内容报告和编辑预览工作台处理审核，不安排 CMS 开发。
- 托管产品已确定为 Pages；上线前实测中国大陆及其他目标地区网络。首屏避免外部字体，正文和搜索索引随静态产物部署。检查生产域名可索引、Preview 默认 noindex、生产 pages.dev 重定向以及真实 404。

已购主域名为 `promiliaguide.com`，Astro site 固定为 `https://promiliaguide.com`。DNS/构建细节见 `DOMAIN-AND-PAGES.md`，语言结构与发布流程见 `LOCALIZATION-PLAN.md`。根域名使用 Pages 时需将 DNS zone 配置到对应 Cloudflare 账户，先在 Pages 中关联域名再验证解析与 HTTPS。

建议数据模型：

```text
Source: id, title, publisher, url, publishedAt, checkedAt, gameVersion, timecode
Claim: id, text, sourceRefs[], type, gameVersion, verification, affectedPages[]
Guide: slug, title, description, author, publishedAt, updatedAt, gameVersion,
       gameRegion, contentId, locale, sourceRevision, translatedFromRevision,
       translationStatus, reviewer, verification, sourceRefs[], relatedEntities[], body
Entity: id, slug, name, type, gameVersion, sourceRefs[], verifiedFields,
        unknownFields[], relatedGuides[]
```

页面更新时间只在正文或事实发生实质变化时更新。来源核对时间独立显示，避免把「今天检查过」等同于「今天有新攻略」。

## 6. 发布与运营

第一周先开放核心内容让搜索引擎开始发现页面，但不预设短期收录或排名保证。通过站长平台提交 Sitemap，观察抓取错误和实际搜索词。

对外内容以原创速查表、机制解释和实测截图为主；发布到自己的 B 站、TapTap 等账号时遵守平台规则并给出相关原文入口。发帖、联系作者和社区推广均作为后续运营工作，不由本方案自动执行。

先建立复访价值：开荒清单、清楚的修订记录、资源与机制的持续核验。流量和维护投入明确后，再评估广告或其他商业化；推广链接需要透明标注。

## 7. 资源与成本边界

- 工时：按每天 3—4 小时，准备期约 36—48 小时，公测前后另预留集中更新时段。
- 支出：域名已经购买，实际成交价尚未提供，不沿用查询报价作为实际支出。先评估 Pages 免费计划是否满足首版；原 300 元建议预算不含人工，翻译校对如需外包应另估。
- 账号与第三方服务：域名已定；上线前完成对应 Cloudflare 账户中的 DNS、Pages、统计与纠错渠道配置。方案更新未执行这些云端操作。
- 内容边界：使用公开资料，不收集玩家账号密码，不把未经公开许可的测试材料纳入采集范围。

## 8. 成功标准

### 公测前必须达到

- 首版目标简中 18—20、日语 8—10，合计 26—30 个实质语言 URL；校对不足时减少次要主题，保留双语核心路径。
- 影响玩家决策的结论全部能回溯来源或明确标记为编辑建议/待核验。
- 所有公开页标明适用版本；关键系统准备好公测核验清单。
- 手机首页 → 相关攻略最多两次点击；搜索可覆盖名称与常见简称。
- 关键页面完成移动端实测，构建、内链和部署检查通过。
- 双语术语与地区说明完成审核；语言切换、当前语言搜索、双向 hreflang 和译文修订状态正确。

### 公测后第一周观察

- 关键页面每天至少检查一次；已确认的重大错误优先当日修订。
- 记录搜索无结果词、纠错类型、站内跳转和复访趋势，安排后续选题。
- 以实际搜索曝光、可用页数和更新负担建立基线，再决定增量目标。
